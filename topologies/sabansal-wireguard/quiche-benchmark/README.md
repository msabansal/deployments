# cloudflare/quiche encrypted goodput benchmark

This harness uses the upstream `quiche-server` and `quiche-client` apps from
[quiche 0.30.0](https://github.com/cloudflare/quiche/releases/tag/0.30.0),
released September 17, 2026. The source is pinned to
`be47c5011215b9f13bad06bd7627d3ae49888a19`; `Cargo.lock` pins the complete upstream
workspace, including BoringSSL via `boring` 5.2.0. Builds use `cargo build
--locked --release`, native CPU code generation, native optimized C/C++, thin
LTO, and one Rust codegen unit. No fuzzing, null cipher, disabled verification,
session resumption, or 0-RTT is used.

This is **HTTP/3 application-body goodput over QUIC v1/TLS 1.3**, not an IP
tunnel or a WireGuard-compatible topology. It transfers generated bytes over
the private VNet, with no `wg0` route. The benchmark does not write or print
payload data. The server cyclically sends a 64 KiB generated buffer as one
long HTTP/3 body per requested stream. The benchmark client counts actual
`recv_body()` bytes during a common, monotonic-clock measurement window and
discards them. HTTP headers, QUIC overhead, retransmissions, and warmup bytes
are excluded from goodput.

## Run

From the topology directory:

```powershell
.\test-quiche-throughput.ps1 -DurationSeconds 30 -ParallelConnections 4 `
  -ServerWorkers 2 -CongestionControl cubic -OutputPath "$env:TEMP\quiche-forward.json"

.\test-quiche-throughput.ps1 -SkipInstall -Reverse -DurationSeconds 30 `
  -OutputPath "$env:TEMP\quiche-reverse.json"

.\test-quiche-throughput.ps1 -SkipInstall -DurationSeconds 30 -KeepServerRunning `
  -OutputPath "$env:TEMP\quiche-persistent.json"

.\test-quiche-throughput.ps1 -SetupOnly -DisablePacing `
  -OutputPath "$env:TEMP\quiche-setup.json"
```

`-SetupOnly` installs or reuses and validates the binaries on both VMs, generates
and validates the certificate/trust anchor, starts the selected server with the
requested settings, and enables it for boot. It **implies server retention**,
including permanent UDP permissions when firewalld is active, without launching
a benchmark client or CPU measurement. It returns a separate setup object with
`mode="setup"`, `status="ready"`, `measurement_performed=false`, server/boot
status, both builds, actual server settings, and certificate fingerprint/expiry.
There are no throughput or CPU fields and no invented zero-throughput result.
Certificate validation here is an OpenSSL chain, DNS, validity, and server-purpose
check; no QUIC handshake or negotiated-cipher measurement is performed.
`-SkipInstall`, `-Reverse`, tuning options, and `-OutputPath` work in this mode.
Deployment integration should invoke the wrapper in all Quiche deployments:
map `-SkipThroughputTest` to `-SetupOnly`; otherwise pass `-KeepServerRunning`
to measure and retain the server.

The default deployment is `sabansal-wireguard-sea-rg` / `sabansal-wireguard`.
The wrapper resolves VM names and private/public IPs from Azure deployment
outputs. SSH with `azureuser` is the default fast transport; use
`-SshIdentityFile` for a nondefault identity or `-Transport RunCommand` for
Azure VM Run Command. SSH accepts previously unseen host keys while rejecting
changed known keys. The first run installs missing Azure Linux build tools
and builds on both VMs. Subsequent runs reuse binaries with the same source
and instrumentation fingerprint; `-SkipInstall` also skips uploading the
harness. Before starting a server or measurement, both VMs must have executable
client/server binaries that pass an application-identity `--help` probe, recorded
quiche version 0.30.0, the pinned commit, and the **current local** compiled-source
fingerprint. The SHA256 input is the concatenation of `instrument.py`, `bench.rs`,
`Cargo.lock`, and `install.sh`, in that order, normalized to UTF-8 without a BOM
and LF line endings, exactly as uploaded to the installer. The upstream apps
have no runtime `--version` option; version verification uses build provenance,
not a binary hash or independent attestation. After changing harness files,
run once without `-SkipInstall`. Python harness updates do not change the
compiled-source fingerprint or force recompilation.
The two Python runtime files are also compared against SHA256 hashes of their
current local normalized sources, independently of the compiled fingerprint.
`-SkipInstall` rejects stale runtime files even if their CLI options match.
Release build intermediates are cleaned after installation because the
Azure Linux image's root filesystem is small.

Tuning parameters include `-CongestionControl cubic|bbr`,
`-ParallelConnections 1..32`, `-ServerWorkers 1..2`,
`-StreamsPerConnection 1..32`, `-ConnectionWindowBytes`,
`-StreamWindowBytes`, `-InitialCongestionWindowPackets`,
`-MaxUdpPayloadBytes 1200..1472`, `-DisableGso`, `-DisableGro`,
`-DisablePacing`, and `-PinProcesses`. UDP payloads are capped at the IPv4
MTU-safe maximum for a 1500-byte underlay. **NIC MTUs are never changed.**

`-PinProcesses` is an **opt-in locality experiment**, not hardware offload.
After each `Popen`, Linux `sched_setaffinity` pins the two upstream server
workers to the first two sorted CPUs in that VM's current allowed affinity
mask; receiver connection processes alternate between those two allowed CPUs.
On these VMs the masks are `[0]`, `[1]` for workers and `[0]`, `[1]`, `[0]`,
`[1]` for four receivers. Restricted/noncontiguous CPU lists are respected
(for example `[2,6]`); larger VMs still use the first two allowed CPUs rather
than all CPUs. A single process uses the first allowed CPU. With two or more
processes, fewer than two allowed CPUs is an explicit error, not a silent
fallback. Applied masks are queried back and verified. Pinning failures terminate
only the already-started children. Supervisors, CPU sampling, IRQs, RSS, and
XPS are not pinned or retuned by this option.

Both pinned and automatic runs report allowed CPUs and each child's PID and
actual `cpu_affinity` snapshot immediately after launch: server telemetry under
`server_runtime.workers`, receiver telemetry under `receiver_results`.
`settings` records `pin_processes_requested`, `server_process_affinities`, and,
for measurements, `client_process_affinities`. `-SetupOnly -PinProcesses`
persists server worker pinning but starts no receiver. Defaults remain unpinned;
no throughput gain is assumed until measured.

For the first affinity trial, run **without** `-SkipInstall` to upload the
updated Python harness; matching Rust binaries are reused without compilation.
Afterwards, a comparison can use `-SkipInstall -DurationSeconds 30
-DisablePacing -PinProcesses`, omitting `-PinProcesses` for the automatic
control and adding `-Reverse` for the other direction. Both runtime harness
help probes must advertise the new option before startup, so stale Python
files are rejected even when the compiled-source fingerprint still matches.

The default uses two upstream server processes on UDP ports 4433 and 4434
and four client connections with one stream each, Cubic, a 64 MiB connection
window, a 4 MiB stream window, and 1472-byte UDP payloads, distributing work
over the two SMT vCPUs. GSO, GRO, and pacing are enabled by default.
Both ports are private-VNet traffic; no public QUIC NSG rule is required.
By default, the selected server's dedicated `quiche-benchmark` systemd service
is stopped and disabled in `finally`, including failed measurements.
`-KeepServerRunning` instead enables and retains that server **after a successful
measurement**; `-SetupOnly` retains it after successful setup without measurement.
Both preserve the selected tuning and worker count. With `-Reverse`,
the retained server is the original client VM. The unit is
`/etc/systemd/system/quiche-benchmark.service`, with
`WantedBy=multi-user.target`, network-online ordering and dependency,
`Restart=on-failure`, and `RestartSec=2`. Its supervisor and binaries reside in
`/opt/quiche-benchmark-harness/server.py` and `/opt/quiche-benchmark/bin/`.
When firewalld is active, keep mode retains runtime and permanent
`4433-4434/udp` permissions in its default zone without a global firewall
reload. Normal/failure cleanup removes only firewall permissions added by
that invocation; pre-existing rules are preserved. The CPU collection service,
`/etc/systemd/system/quiche-benchmark-cpu.service`, is always stopped after the
test, even in keep mode. Only dedicated processes and temporary uploads are
cleaned up; no broad process termination is used.
Readiness and GSO telemetry are scoped to the current systemd invocation ID,
not just a PID that can be reused after reboot. A restart during measurement
or persistence confirmation fails explicitly rather than reporting a new
instance's counters or stale process affinities as the measured instance.

## Measurement and proof

The server generates a short-lived self-signed certificate with a DNS SAN
for `quiche-benchmark.internal`. Only its public certificate is copied to
the receiver as an explicit trust anchor. `--connect-to` selects the private
address while TLS validates the DNS identity. The client requires a complete
handshake, a peer certificate, HTTP/3 ALPN, and non-early-data operation. JSON
records the actual negotiated AEAD (validated runs negotiated `AES128_GCM`).

The certificate is valid for **seven days**. The wrapper regenerates it if
missing or within one hour of expiry, restarts the selected server, and copies
the public trust anchor to the receiver. Server certificate/key paths are
`/opt/quiche-benchmark/cert.pem` and `/opt/quiche-benchmark/key.pem`; the receiver
uses `/opt/quiche-benchmark/server-cert.pem`. Keep mode does **not** provide
automatic renewal or trust rotation: rerun the wrapper within the last hour
of validity (or after expiry) to regenerate and redistribute the certificate,
using `-KeepServerRunning` again to retain the refreshed service. A reboot alone
neither refreshes the certificate nor changes the receiver's trust anchor.

The client processes share a scheduled start timestamp, translated once to
monotonic clocks. They establish connections and transfer body bytes before
measurement starts. `WarmupSeconds` is a minimum launch allowance; scheduling
and control-plane setup can add warmup time. Each connection records its
actual premeasurement body-transfer interval. Receiver processes share one
VM clock; CPU samplers on both VMs use the same UTC interval and require
synchronized VM clocks. VM CPU percentages average both vCPUs, not one core.

JSON preserves each connection's measured application bytes, seconds and
calculated bits/s; the aggregate is `sum(bytes_received) * 8 / duration_seconds`.
It also records both VM CPU intervals, source/build fingerprints and compiler
flags, congestion/window/MTU/offload choices, and actual server GSO/pacing
settings. Client results are gzip/base64 encoded during transport to avoid
Azure Run Command's 4 KiB output limit, then decoded into ordinary JSON.

Linux software UDP GSO is used even though MANA reports
`tx-udp-segmentation: off [fixed]`. Actual successful GSO `sendmsg()` calls
are counted. Client `UDP_GRO` uses `recvmsg()` ancillary segment lengths,
passing individual UDP datagrams to the unchanged upstream QUIC event loop;
actual GRO batches and receive syscalls are recorded. Both sides request
16 MiB socket buffers. Pacing reports acceptance of `SO_TXTIME` and quiche
pacing configuration; it does not independently certify the NIC's qdisc.
Both measurement and setup results include
`settings.kernel_busy_polling.server` and `.client`, each containing the actual
`busy_poll` and `busy_read` values read from `/proc/sys/net/core` during preflight.
These correspond to the selected roles, including reverse mode, and are kernel
values in microseconds, not requested deployment flags or proof of active
per-socket polling. Missing or unreadable probes and values that are not
nonnegative integers fail explicitly. The wrapper only observes these settings;
it never changes them.

`instrument.py` applies exact-source patches and fails on changed anchors.
Changes retain upstream UDP/recovery logic, discard body output before string
conversion, add timed receiver counters, make the small generated body repeat,
and permit GSO without requiring pacing. It also fixes benchmark-mode sender
fairness: the upstream example stops after the first saturated connection's
send burst, which starves later connections with an endless body. The harness
visits the remaining connections before the next event-loop iteration.

## Validated hardware results

On Azure Linux 4, Standard_D2als_v7, Southeast Asia zone 1, AMD EPYC 9V45
(one physical core / two SMT vCPUs), 30-second measurements with 1472-byte UDP
payloads, GSO/GRO, Cubic, two server workers and four client connections reached
**7.923 Gbit/s forward** and **8.126 Gbit/s reverse** application-body goodput.
Server CPU was approximately 100%; receiver CPU was approximately 84-89%.
One server worker was limited to approximately 5.4-5.9 Gbit/s. Eight connections
and BBR did not beat the two-worker/four-connection Cubic result in the measured
sweep. These are measured runs, not guaranteed bandwidth or an exhaustive
global optimum; raw result artifacts belong outside the repository.
Subsequent parent-run 30-second measurements with the 4 MiB stream-window
setting reached **8.785 Gbit/s forward** and **8.602 Gbit/s reverse**.
